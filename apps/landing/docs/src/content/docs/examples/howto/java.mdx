This walkthrough takes you from an empty directory to a merged feature on a small **Java CLI** project (Maven + JUnit 5). It also covers the Gradle variant — the only differences are the wrapper and the test command.

## Prerequisites

You should already have done the [common setup](/docs/examples/howto/): `npm install -g karajan-code`, `kj init` inside the project, and a green `kj doctor`. If `kj doctor` is red, fix that first — `kj run` will refuse to start otherwise.

You'll also need JDK 17+ (`java --version`) and either Maven 3.8+ (`mvn --version`) or a Gradle wrapper.

## Walkthrough

<Steps>

1. **Bootstrap the project.**

   ```bash
   mkdir hello-java && cd hello-java
   mvn -q archetype:generate -DgroupId=dev.kj.hello \
     -DartifactId=hello-java -DarchetypeArtifactId=maven-archetype-quickstart \
     -DinteractiveMode=false
   mv hello-java/* . && rm -rf hello-java
   git init -b main && git add -A && git commit -m "chore: scaffold"
   ```

   Open `pom.xml` and bump JUnit to 5, plus add the surefire plugin so `mvn test` runs JUnit 5:

   ```xml
   <properties>
     <maven.compiler.source>17</maven.compiler.source>
     <maven.compiler.target>17</maven.compiler.target>
     <junit.version>5.10.2</junit.version>
   </properties>

   <dependencies>
     <dependency>
       <groupId>org.junit.jupiter</groupId>
       <artifactId>junit-jupiter</artifactId>
       <version>${junit.version}</version>
       <scope>test</scope>
     </dependency>
   </dependencies>
   ```

   <Aside type="tip" title="Why JDK 17+">
   Karajan's coder defaults to modern Java syntax (records, switch expressions, `var`). On JDK 11 you'd get reviewer rejections asking for backports. If you're stuck on 11, declare it explicitly in the run command and the planner adjusts.
   </Aside>

2. **Initialize Karajan in the repo.**

   ```bash
   kj init
   kj doctor
   ```

   `kj init` creates `.karajan/` and writes the orchestrator config; `kj doctor` confirms the agent CLIs, Docker, Ollama, ports, and detects the JDK + build tool.

3. **Describe the feature in natural language.**

   No spec file. No JSON. Just the task as you'd describe it to a colleague:

   ```bash
   kj run "Add a static method 'greet(String name)' to \
   src/main/java/dev/kj/hello/Greeter.java that returns 'Hello, <name>!'. \
   Add a JUnit 5 test in src/test/java/dev/kj/hello/GreeterTest.java \
   that asserts the output for the name 'world'." \
     --methodology tdd \
     --coder claude \
     --reviewer codex \
     --reviewer-fallback claude \
     --max-iterations 5
   ```

   <Aside type="note" title="What's happening under the hood">
   With `--methodology tdd`, Karajan writes the failing test first, then the implementation, then runs `mvn test`. The reviewer (Codex by default, Claude as fallback) checks the diff. If the reviewer rejects, Karajan loops the coder again — up to `--max-iterations`. The tester adapter recognises Maven via `pom.xml` and Gradle via `build.gradle(.kts)` automatically.
   </Aside>

4. **Watch the run on the HU Board.**

   Open [http://localhost:4000](http://localhost:4000) in another tab while the pipeline runs. You'll see, in real time:

   - Each role activating (planner → coder → tester → reviewer).
   - The exact prompt + response of every agent call.
   - The diff after each iteration.
   - Maven's surefire output (or Gradle's test report) line by line.
   - The reviewer verdict.

   You can also tail the same trace in the terminal:

   ```bash
   kj tail
   ```

5. **Inspect the result.**

   ```bash
   git status
   git diff --stat
   mvn test
   ```

   Expected output of `mvn test`:

   ```
   [INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
   [INFO] BUILD SUCCESS
   ```

6. **Merge.**

   Karajan does not push or merge for you by default — that's your call. When you're happy with the diff:

   ```bash
   git checkout -b feat/greeter
   git add -A && git commit -m "feat: add Greeter.greet(name)"
   git push -u origin feat/greeter
   gh pr create --fill
   ```

   Or, if you want Karajan to also open the PR for you, add `--auto-commit --auto-pr` to the `kj run` invocation.

</Steps>

## Possible errors and how to clear them

<Aside type="caution" title="`mvn: command not found`">
Install Maven (`brew install maven` on macOS, `sdk install maven` via SDKMAN on Linux). The Karajan doctor flags missing build tooling but won't install JVM toolchains for you.
</Aside>

<Aside type="caution" title="Reviewer rejects with `JUnit 4 imports leaking`">
The archetype scaffolds JUnit 4 by default. Make sure the dependency in `pom.xml` uses `junit-jupiter` (Jupiter = JUnit 5). The coder migrates the imports automatically on iteration 2 if needed.
</Aside>

<Aside type="caution" title="`kj run` exits with `no coder configured`">
Run `kj doctor` and follow the agent-CLI install instructions. The most common cause is having Claude installed but without a logged-in session (`claude login`).
</Aside>

<Aside type="caution" title="Pipeline stalls at `coder:hibernate`">
You hit a quota cap. Karajan persists the session to `~/.karajan/standby/<sessionId>.json`; resume it with `kj standby list` then `kj standby resume <sessionId> --force` after the cap resets.
</Aside>

## Variants

<Tabs>
<TabItem label="Gradle (Kotlin DSL)">

Same flow, different build tool. Bootstrap with the Gradle wrapper:

```bash
mkdir hello-java && cd hello-java
gradle init --type java-application --dsl kotlin --test-framework junit-jupiter
git init -b main && git add -A && git commit -m "chore: scaffold"
```

Then run the same `kj run` invocation. Karajan auto-detects `build.gradle.kts` and uses `./gradlew test` instead of `mvn test`.

</TabItem>
<TabItem label="With MCP">

The same run launched via the MCP from any MCP-capable client (Cursor, Claude Desktop, Codex):

```json
{
  "tool": "kj_run",
  "params": {
    "task": "Add a static method 'greet(String name)' returning 'Hello, <name>!'. JUnit 5 test.",
    "methodology": "tdd",
    "coder": "claude",
    "reviewer": "codex",
    "reviewerFallback": "claude",
    "maxIterations": 5
  }
}
```

</TabItem>
<TabItem label="Stricter quality gate">

Add `--mode strict` and the deterministic security collectors:

```bash
kj run "<task>" \
  --mode strict \
  --enable-security \
  --enable-sonarcloud \
  --methodology tdd
```

This wires the OSV-Scanner and Semgrep collectors into the audit (Java ruleset enabled), and gates the merge on the Sonar quality gate as well as the reviewer verdict. Sonar's Java analyser is particularly strong on null-safety and resource leaks.

</TabItem>
</Tabs>

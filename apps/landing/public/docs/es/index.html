¿Por qué Karajan Code?

Sección titulada «¿Por qué Karajan Code?»

Tu agente de IA (Claude Code, Codex, Gemini CLI, Cursor…) escribe el código — Karajan gobierna cómo ocurre. kj instala un método que tu agente sigue en cada tarea (RAG antes de suponer, card primero, tests primero) y lo hace cumplir con gates de git: cada commit exige el veredicto de una IA distinta, los hallazgos de seguridad no los anula nadie, y la rama base solo se mueve por PR. El que hace nunca se califica a sí mismo — y el falso verde es estructuralmente imposible.

Un runtime de loop engineering

Sección titulada «Un runtime de loop engineering»

El prompt engineering sacaba una buena respuesta de un buen prompt. El context engineering curaba lo que veía el modelo. La frontera de 2026 es el loop engineering: dejas de promptear al agente a mano y diseñas el sistema que lo promptea, lo verifica y decide qué pasa después — hasta que se cumple el objetivo o te lo devuelve a ti. Karajan se construyó alrededor de ese bucle antes de que el término calara:

  • Separación maker / checker — un coder contra roles independientes de reviewer, tester y security, con Solomon arbitrando los conflictos. El maker nunca corrige su propio trabajo.
  • Verificación determinista — TDD, tests de aceptación por HU, gates de SonarQube y guardarraíles deterministas. Verificar es tests, no intuición.
  • La escalera de autonomía L1 → L2 → L3 — el eje interactive | assisted | autonomous (v3.7.0). Informe, luego fixes asistidos, luego kj autorun desatendido — con default interactive, así que tú decides.
  • Un spine de estado duradero — sesiones, el HU Board, journals, el índice RAG y kj resume mantienen vivo el bucle entre runs.

El caveat que el loop engineering recalca — los bucles desatendidos cometen errores desatendidos — está diseñado de serie: los runs autónomos listan sus defectos residuales, cada historia aterriza tras una PR, y kj-trash hace snapshot de las operaciones destructivas. v4.60.0: atril entra en la familia (actual)

Sección titulada «v4.60.0: atril entra en la familia (actual)»

atril es el módulo de la familia para skills, comandos y subagentes: los guarda en un almacén fuera de lo que cada CLI de IA carga al arrancar y resuelve solo lo que pide cada tarea, para todas las CLIs. Esta versión trae sus siete primeros pasos (validar, escanear, enriquecer, grafo, buscar, resolver con presupuesto, instalar). v4.59.0: una review con ojos de QA

Sección titulada «v4.59.0: una review con ojos de QA»

kj review --third-party --lens qa juzga una PR como lo haría alguien de QA: comportamiento nuevo sin test, tests que no pueden fallar, esperas inestables, selectores frágiles, escenarios que faltan. v4.58.0: la review cruzada, probada en CI

Sección titulada «v4.58.0: la review cruzada, probada en CI»

kj review --verify-pr hace fallar una PR cuando a un commit le falta la review cruzada publicada, y un workflow nuevo, cross-ai-verdict, lo ejecuta en cada PR. kj review --third-party respeta la lista allow de privacidad del propio repo revisado, leída en la base para que una PR no pueda eximirse a sí misma. Donde el sandbox del host ya deniega sus rutas, las guardas del Sentinel que leen la shell se apartan: menos falsos positivos y ninguna protección perdida. Tras actualizar, hay que resellar.

kj review --third-party revisa ya un fichero nuevo que no cabe en un lote en trozos de líneas, con sus números de línea correctos, así que la cobertura llega al 100 %. advice.split agrupa una PR de Maven o Gradle por paquetes en vez de meter todo lo de src/test/java en un solo trozo.

v4.57.2: consejo para partir una PR grande

Sección titulada «v4.57.2: consejo para partir una PR grande»

v4.57.1: una PR grande revisada entera

Sección titulada «v4.57.1: una PR grande revisada entera»

kj review --third-party revisa el diff entero de una PR grande por lotes de ficheros completos, dice en coverage qué ha revisado y nunca aprueba código que no ha visto (verdict.status: partial). Los requisitos de la casa van aparte en policyChecks, y un par de coordenadas GPS ya no se toma por un teléfono.

v4.57.0: el sistema operativo guarda el carril

Sección titulada «v4.57.0: el sistema operativo guarda el carril»

kj harden activa el sandbox de Bash de Claude Code donde puede arrancar en la máquina: las escrituras se quedan en el proyecto (más el estado de kj y las cachés de paquetes), y el supervisor y la clave del móvil quedan fuera de alcance. Donde no arranca, no se escribe nada y kj dice qué falta. Un job nuevo de CI falla con cualquier vulnerabilidad crítica en los lockfiles del repo, y las que había hoy están cerradas. Además: un despliegue ya no se trata como una release, el release check dice cuándo hay que renovar el sello, y kj harden siembra ESLint con el parser de TypeScript en los proyectos TypeScript.

v4.56.0: revisar la PR de otra persona

Sección titulada «v4.56.0: revisar la PR de otra persona»

kj review --third-party --json permite a un agente revisor revisar la PR de otra persona con el reviewer de kj y las reglas del repo destino, y devuelve un único JSON con el veredicto, los hallazgos y los requisitos de la PR (tamaño, commits, tests, secretos, datos personales, dependencias arriesgadas, semgrep, Sonar), sin las gates del trabajo propio y sin guardar veredicto. El Sentinel deja de leer shell donde ya decide un punto de control (actos humanos, identidad, push), pre-push comprueba la identidad de cada commit que sube, y el bloqueo del Steward también para un commit.

v4.55.0: cada HU con el modelo que pide su tramo

Sección titulada «v4.55.0: cada HU con el modelo que pide su tramo»

El coder de cada HU corre con el modelo y la intensidad que pide su tramo (trivial, estándar o deep) y sube al más capaz cuando una iteración falla; un modelo que hayas elegido siempre gana y el reviewer nunca se enruta. kj plan rellena el modelo de cada HU a partir de su tramo, el HU Board puede cambiarlo y kj report dice cuántas HUs se enrutaron y cuántas subieron. Las reviews en paralelo en una misma máquina comparten plazas de sonar-scanner, un reviewer ya no bloquea una funcionalidad de una plataforma que simplemente no conoce, y kj handoff add pasa el Sentinel.

v4.54.0: las skills llegan a los prompts y tienes una ventana de tareas

Sección titulada «v4.54.0: las skills llegan a los prompts y tienes una ventana de tareas»

Las skills que encajan con la tarea (primero las del proyecto, luego las del catálogo local) llegan al coder y al reviewer, hasta 3 por rol, y al arrancar una HU se nombran. kj handoff watch muestra en otra terminal lo que solo puedes hacer tú (publicar, sellar, ejecutar un script), con fecha y motivo, fuera del scroll de la sesión. kj env install conecta el MCP de qmd para que el agente le pregunte por documentos, notas, ADRs y planes, y al RAG por el código. Y rag-first cuenta una respuesta de kj_rag_query que llega cortada.

v4.53.1: las PRs apiladas pasan board-sync

Sección titulada «v4.53.1: las PRs apiladas pasan board-sync»

La siguiente PR de una card partida en PRs apiladas se puede subir y abrir antes de mover la card de la primera, un push ya no contradice la respuesta que board-sync acaba de darle, un bloqueo que kj no pudo comprobar dice por qué (casi siempre otra cuenta de gh activa), y un título de card o un mensaje de commit que solo menciona sellar el harness o enrolar el móvil se lee como texto.

v4.53.0: el móvil deja de estorbar

Sección titulada «v4.53.0: el móvil deja de estorbar»

kj init ofrece enrolar tu móvil, kj doctor dice claro qué se rechaza sin él, y sin ningún móvil una persona en la terminal puede bajar el nivel. kj review --publish-pr deja en la PR los veredictos de la otra IA como una review de GitHub, kj review avisa de dependencias publicadas hace horas, kj harden dice cómo hacer obligatorios los checks del método, y arrancar una card la reserva para un equipo. Cada HU registra ahora el modelo y el coste de su coder, y kj report los suma por modelo; además sale de la descomposición con su tramo, y kj run --profile frugal|standard|deep elige los modelos. Un plan dice si cada cambio amplía, regenera o reconstruye código existente, y regenerar exige una licencia según el mutation score del módulo. La cuarentena de dependencias puede bloquear, kj check avisa de cuándo toca auditar, y los patrones de prompt-injection pasan a un catálogo que lee toda la familia.

Ninguna versión se publica sin la batería de escenarios en verde, y la CI la ejecuta en cada PR. kj worktree prune retira los carriles de kj que están demostrablemente abandonados, una corrección del revisor se nombra como el método funcionando, y el veredicto de un revisor claude se lee aunque su respuesta empiece con eventos de hooks.

v4.49.3: prompts grandes que caben

v4.49.2: runs de plan que implementan su HU y un Sentinel que lee comandos

Sección titulada «v4.49.2: runs de plan que implementan su HU y un Sentinel que lee comandos»

Un run de plan ya no hace el triage del encargo original del plan: generaba otras HUs que se ejecutaban en lugar de las del plan, perdía sus Gherkin y podía saltarse el coder y aprobar un diff vacío. Una HU de código ya no se aprueba con la suite del proyecto en rojo, y la primera release de un repo recién preparado ya no se bloquea por los ficheros que instaló su propio setup. El Sentinel deja de reaccionar a palabras dentro de texto entrecomillado, acepta el kj rag query que él mismo recomienda y ya no toma la ruta de un fichero de cuerpo por una atribución. El E2BIG pasa enseguida al siguiente proveedor, los rangos de versión ya no son secretos y el audit se queda con las issues de Sonar del proyecto actual.

v4.49.1: runs de plan que commitean y un presupuesto de tamaño que no pregunta

Sección titulada «v4.49.1: runs de plan que commitean y un presupuesto de tamaño que no pregunta»

kj run --plan se paraba antes de commitear cada HU, bloqueado por sus propios gates de card-first y de veredicto, volvía a revisar el spec del plan y nunca le pasaba al coder el contexto de dominio; las tres cosas están arregladas, y el contexto de dominio llega ahora al coder en todos los runs. El tamaño de PR tiene dos tramos: unas 150 líneas es lo ideal, hasta 200 se permite sin preguntar y por encima se parte. kj harden --report nombra ahora el Sentinel y los git hooks cuando faltan, y kj harden ya no pide sellar sin nada que sellar.

v4.49.0: planes que convergen, gates que dejan de gritarle a kj

Sección titulada «v4.49.0: planes que convergen, gates que dejan de gritarle a kj»

Cinco avisos de campo de una misma sesión contra kj plan: el bucle de arreglo archivaba HUs con un estado que validate rechazaba, solo sabía añadir dependencias y podía cerrar un ciclo que luego llegaba al run. Ahora las HUs archivadas validan y las sustitutas heredan sus aristas, el fixer quita dependencias y recorta alcances cuando el feedback lo pide, y un ciclo se nombra y para el run. El gate de privacidad ya no toma un id de plan por una tarjeta, pr-size deja fuera el plan compartido, el catálogo de skills ya no mete fixtures de test en el proyecto y las guardas que CI no ve las avala la firma del padrón.

Tras actualizar kj, kj release check negaba el hook que un humano había sellado con la versión anterior, porque lo recomputa con la plantilla nueva. v4.48.1: tres arreglos de campo

Sección titulada «v4.48.1: tres arreglos de campo»

El workflow de calidad corre en la raíz del lenguaje cuando la app vive en un subdirectorio, kj rag query ya no reindexa el repo entero antes de responder cuando el índice es antiguo, y el rag-first deja editar un barrel (index.ts, __init__.py, mod.rs) en cuanto el RAG ha respondido sobre su carpeta.

v4.48.0: lo que un gate negó, registrado

Sección titulada «v4.48.0: lo que un gate negó, registrado»

El agente ya no pide al humano por el chat lo que kj le negó. Cada deny del Sentinel deja un registro con las palabras del propio gate, y kj handoff add registra un encargo solo contra ese registro, así que el porqué es del gate, nunca del agente; kj handoff list|show lo leen por identificador. Además: sacar del índice un fichero de runtime heredado ya no exige --no-verify, y el agente puede reportar con kj report-issue, justo el comando al que lo manda el Sentinel.

v4.47.0: el nivel que protege a quien no sabe que existe el riesgo

Sección titulada «v4.47.0: el nivel que protege a quien no sabe que existe el riesgo»

Seguridad máxima por defecto: todo acto del catálogo (sellar el supervisor, aprobar reglas, enrolar otro móvil, bajar el nivel) se firma desde el móvil sobre los bytes exactos y sin móvil se niega; kj security show|normal|max lee y cambia el nivel, y bajarlo es un acto firmado que dice qué se hace y por qué. Un móvil perdido se sustituye con el código de recuperación de un solo uso que se enseña al primer enrolamiento, nunca reinstalando: el código se gasta al usarlo, se emite otro y el móvil perdido queda revocado. CI juzga cada cambio del padrón de móviles. Y las reglas del relé, que desde 4.46 rechazaban todos los sellos con 403, admiten lo que la página de firma enseña.

v4.46.0: lo que firma el móvil, dicho

Sección titulada «v4.46.0: lo que firma el móvil, dicho»

“Veo ‘sentinel’, pero ¿qué estoy firmando? me puedes estar engañando”. La petición de firma lleva ahora qué cambia, fichero a fichero: nuevo, modificado o borrado, líneas añadidas y quitadas, un resumen de una línea, el diff (recortado y pasado por el escaneo de privacidad), la rama y qué la generó. La página habla el idioma del navegador, español o inglés, pliega el diff bajo cada fichero y dice que los sha256 que muestra son lo que la firma garantiza. Además: un catálogo cerrado de actos humanos con un solo mecanismo y un test de arquitectura que lo vigila (enrolar el móvil ejecuta las cuatro capas por sí mismo), y los criterios de la card llegan a las HUs al descomponer, para que ninguno se quede sin HU.

v4.45.0: aprobado significa que los criterios de la card están en el diff

Sección titulada «v4.45.0: aprobado significa que los criterios de la card están en el diff»

Un run terminó aprobado sin implementar ninguno de los tres criterios de aceptación de la card. Con card leída, una IA distinta del coder lee ahora cada criterio contra el diff antes de que el run diga aprobado y contesta uno a uno: cubierto, con la evidencia, o no. Un criterio sin cubrir vuelve al coder; en el camino de HUs el resultado dice approved:false con la lista; un juez sin veredicto legible nunca concede una aprobación. Además: kj harden tras subir de versión ya no se bloquea contra el sello, y kj update nunca degrada un kj enlazado desde su árbol fuente.

v4.44.1: el run dice lo que no pudo hacer

Sección titulada «v4.44.1: el run dice lo que no pudo hacer»

Seis reportes de campo de un mismo día sobre un proyecto recién creado: un run aprobado sin push y sin PR y sin decirlo, cinco commits con dos identidades, ramas con nombre de HUs inventadas, una card que no se pudo leer y un pipeline que siguió sin ella, y un agente con kj instalado y nunca endurecido rodeando cada gate a mano. Ahora el push o la PR que falla viaja en el resultado del run con su remedio (el rechazo por el scope workflow nombra el arreglo exacto); la identidad git se resuelve una vez y cada commit del run la lleva; con card la rama es feat/<CARD-ID>-<slug> en los dos caminos; una card que no se puede leer para el run antes de empezar; un host Claude sin el harness del Sentinel también lo para, y una issue para karajan-code sale por kj report-issue. La primera sesión de cada versión invita a enrolar el móvil (ADR 0018).

v4.43.0: el pipeline commitea solo lo suyo

Sección titulada «v4.43.0: el pipeline commitea solo lo suyo»

Un run aprobó un paso con el reviewer desactivado, sin implementación y con un test en rojo, stageó 22 ficheros del harness en el commit y commiteó 960 líneas donde el plan permitía 150. Ahora una tarea simple conserva su review cruzada, y sin review el pipeline no sella veredicto ni commitea; con TDD la suite de tests del proyecto corre en cada iteración y una suite en rojo vuelve al coder; el presupuesto de la PR se aplica antes del commit, con el cálculo de kj pr-size; y el commit lleva solo lo que el run cambió, por rutas, con el veredicto atado a ese diff exacto. El Sentinel deniega además git add -A y stagear ficheros de runtime del agente, el hook pre-commit los rechaza lleguen como lleguen, y una pregunta que no cambiaba nada (documentos de dominio) ya no se hace.

v4.42.0: diez reportes de campo, diez arreglos

Sección titulada «v4.42.0: diez reportes de campo, diez arreglos»

Sesiones que trabajaban en otros proyectos reportaron en un día lo que el método les hacía mal, y todo está arreglado. Una revisión aprobada se leía como rechazo porque el revisor envolvía su veredicto en un sobre: ahora lo que kj no puede leer es un fallo del revisor, que se reintenta y se guarda, nunca un defecto que se le cuelga al coder. El ledger del RAG comparaba rutas como texto, así que un índice construido a través de un workspace con symlink descartaba todos los hits y rag-first denegaba cada edición: ahora compara rutas reales y nombra lo que descarta. El coder ya no commitea antes de la review, un fichero temporal fuera del repo no es una fuente, Sonar salta en una línea un repo sin src/, los pipelines de lectura ya no disparan el Sentinel, un timeout del preflight es un aviso, kj status ve un run muerto y kj harden commitea el contrato que genera.

v4.41.0: kj commitea su propio contrato

Sección titulada «v4.41.0: kj commitea su propio contrato»

En un repositorio con historia, kj generó 28 ficheros de contrato y se los dejó al agente, cuyas propias reglas de tamaño de PR prohíben ese commit. v4.18.0 — un kernel, tres tiers

Sección titulada «v4.18.0 — un kernel, tres tiers»

Minor donde la gobernanza deja de ser una feature de kj y se convierte en PAQUETE: @karajan-family/governance llega a npm — Política, Decisión y Excepción como objetos abstractos de primera clase (deterministas, locales, sin LLM), con karajan-code como primer consumidor, no como dueño. La capa de policy completa sus tres tiers: la regla dispara ANTES del daño en tool-time (con el rol del agente que actúa), el diff violador no entra en commit-time, y CI re-verifica el PR contra la misma policy — cubriendo hasta el hook local manipulado. Las excepciones llevan el modelo probatorio completo: quién (identidad), regla exacta, justificación escrita en el momento y caducidad OBLIGATORIA que ejecuta el sistema — la vencida vuelve a bloquear sola, y a la regla concedida tres veces se le dice a la cara que ya no es una excepción sino la política real pidiendo cambio. Cada decisión de chokepoint deja rastro hash-encadenado y anclado en git: reescribir el log de ayer exige reescribir el repo de ayer. Y kj policy add: dices la regla hablando, el motor la valida, y nada se escribe sin tu confirmación.

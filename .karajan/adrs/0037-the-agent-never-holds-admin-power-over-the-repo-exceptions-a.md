# The agent never holds admin power over the repo; exceptions are signed and audited

Status: accepted
Date: 2026-10-29 (accepted 2026-11-01)

## Context

Merging the seal PR (#2754) that moved kj-policy.yml to pull_request_target needed enforce_admins switched off for one merge. The agent works with the maintainer's own gh token, which has admin rights: a capable enough agent could switch the protection off, merge as admin and switch it back, impersonating the maintainer. A phone signature inside kj does not stop that on its own, because GitHub decides and an agent with the token can call the API without passing through kj.

## Decision

Two layers. (1) Prevention: the agent works with a fine-grained token that holds only the repository permissions its work needs: Contents, Pull requests, Issues and Workflows (read and write), Actions (read and write, to re-run failed checks), and Checks, Commit statuses and Metadata (read). It holds no account permission and none of Administration, Environments, Secrets, Variables or Deployments, so it cannot change branch protection, environments, secrets, variables or settings, and cannot approve a protected environment such as `npm-publish` (ADR 0035), even though the token's owner is that environment's reviewer: GitHub's table of permissions for fine-grained tokens lists `POST /repos/{owner}/{repo}/actions/runs/{run_id}/pending_deployments` under Deployments (write), while Actions only reads the pending list. If GitHub ever moves that endpoint under a permission the token holds, this guarantee breaks, so kj doctor's check (KJC-TSK-1268) tries the approval call with the agent's token and expects a refusal. The token still acts as the maintainer, whose admin role could bypass branch protection when merging; what stops that is the protected branch enforcing its rules for administrators too (`enforce_admins`, on for karajan-code's main as of 2026-11-01), which the token cannot switch off without Administration. So the guarantee holds only together with `enforce_admins`, and the detection job checks that it stays on. The maintainer chose (2026-11-01) a fine-grained token of the maintainer's own account rather than a separate agent account or GitHub App: no new account and no new email. A separate identity only helps if the maintainer's admin-capable credentials are out of the agent's reach, because an agent running as the same OS user can read any file of that user; so the admin-capable token (the gh OAuth token with the `repo` and `admin:public_key` scopes) leaves the laptop and its authorization is revoked, and admin acts are done by the maintainer in the browser with passkey or 2FA. kj doctor/audit warn when the token the agent uses has admin power, and the security guide says how to set it up (KJC-TSK-1268, #2462).

The SSH key stays on the laptop for git and the agent can read it too. It grants git operations only (push, fetch, delete or force-push unprotected branches), never the API: it cannot change protection, environments or settings, and branch protection with enforce_admins still applies to it. Hardening it is recommended, not required: a FIDO2 key (`ed25519-sk`) that needs a touch on every use, or at least `ssh-add -c`. Running the agent as another OS user or in a sandbox without read access to `~/.ssh` and gh's config is the long-term goal. (2) Detection: an exception such as a transition admin merge is signed from an enrolled phone like the seal, and a job on every push to main checks that each merge passed its required checks or carries a signed exception, and that the protection is as declared (enforce_admins, required checks); anything else raises an alarm naming the PR and who merged it (KJC-TSK-1269).

## Consequences

The maintainer keeps one GitHub identity, gives the agent a token without Administration, and does admin acts by hand in the browser. The agent can no longer do the transition admin merge itself, which it never should. The agent's acts still appear under the maintainer's account, so detection names the PR and the merge rather than a separate actor. Detection does not prevent abuse by someone holding the maintainer's own credentials, it makes it visible and attributable. Projects where the agent's token has admin power get a warning, not a block.
